# Squirrel, a coverage-guided DBMS fuzzer.
[![build](https://github.com/s3team/Squirrel/actions/workflows/build.yml/badge.svg)](https://github.com/s3team/Squirrel/actions/workflows/build.yml)

### [Original Squirrel repository](https://github.com/s3team/Squirrel)

`Squirrel` is a fuzzer for database managment systems (DBMSs).

`Squirrel` was first built on [AFL](https://github.com/google/AFL) and then migrated to [AFLplusplus](https://github.com/AFLplusplus/AFLplusplus) to enjoy the improvement of state-of-the-art fuzzing strategies.

### This fork
This repository is a fork of the original Squirrel repository, which makes some changes to the mutators:

1. Added the **LLM fixer**, which is a tool that uses a locally run large language model (`qwen2.5-coder-1.5b-instruct-q4_0`) to fix invalid SQL queries generated by the fuzzer. This intends to improve the fuzzing efficiency by increasing the number of valid queries that can actually be executed by the DBMS. This option is enabled by default, but can be disabled by setting the environment variable `USE_LLM=0`.

2. Implemented a more **dynamic selection of mutation strategies** inside the custom mutators. The original Squirrel mutators used a fixed probability and either applied all strategies to a specific IR or none at all. The new mutators will assign dynamic weights to the strategies based on their past performance, as well as take into account the parameters of the tree (such as the number of nodes).

3. Merged the mutators for different DBMSs (except for SQLite, which still has its own), into a single common mutator. This should allow for easier maintenance and future improvements.

4. Added GitHub actions to build and run Squirrel on an HPC cluster (WCSS) - more info below.

We also added the ability to choose a seed for each run using the `SQUIRREL_SEED` environment variable. However, it is worth noting that the results will be random to some extent due to the use of an LLM in the process.

## Currently supported DBMSs
1. SQLite
2. PostgreSQL
3. MySQL
4. MariaDB

## Build Instruction (Run in docker, recommended)

1. Go to the directory of the dockerfile: `cd scripts/dockers/xxx/`, where `xxx` is the database name.
2. Build the docker: `docker build -t xxx .`.
3. Run: `docker run -it xxx`.

If you prefer, you can use the helper scripts instead of running Docker commands manually (run in the root directory of the repo):

1. `scripts/build_docker.sh` builds the database-specific image. The first argument is the database name. This **copies the local repo by default**, or you can run it with `--remote` to clone the repo inside the docker (currently links to the original Squirrel repository!!!).
```bash
./scripts/build_docker.sh sqlite
./scripts/build_docker.sh mysql --remote
```
2. `scripts/run_docker.sh` starts fuzzing and copies the results into `output/`. It accepts an optional second argument for the seed. If omitted, it uses `42` by default.

```bash
./scripts/run_docker.sh sqlite 12345
./scripts/run_docker.sh mysql
```

## Build Instruction (Run on WCSS)

[WCSS](https://wcss.pl/) is a computing service provided by the Wroclaw University of Science and Technology. The following instructions were used for running Squirrel on WCSS, but they should be applicable to other HPC clusters as well.

This was only set up for SQLite, but the workflow can be easily adapted for other DBMSs if proper modifications are made to the corresponding Apptainer definitions.

We rely on github actions to build the apptainer images and run the fuzzing. The results are stored in the `results` directory inside WCSS and will to be manually extracted.

### Available actions

There are 3 actions in the `.github/workflows` directory:
1. `wcss_build.yml`: builds an Apptainer image inside WCSS. You can choose which database to build by setting the `DBMS` variable in the workflow. 
2. `wcss_run.yml`: runs the image built by the build action (you need to run it first). The fuzzing results end up in the `results` directory inside WCSS. You can set various parameters in the workflow, such as maximum runtime and the amount of allocated RAM and CPU cores. You can also choose whether to use the custom mutator from this fork or clone the original Squirrel repository and use its mutator instead.
3. `wcss_zip_results.yml`: this is more of a convenience action, it zips the all the subdirectories in the `results` directory inside WCSS and deletes the original directories. This is useful for downloading the results from WCSS and helps to keep the number of files minimal.

### Setting up secrets
If you fork the repository, you will need to set up your own secrets in the `Settings` tab of your forked repository in order to be able to run the workflows. The secrets are:
- `HOST`: The hostname of the cluster you are using. In case of WCSS, it is `ui.wcss.pl`.
- `USERNAME`: Your WCSS username.
- `PRIVATE_SSH_KEY`: Your private SSH key used for authentication. In case you don't have one, you can generate it with `ssh-keygen` and add the public key to your WCSS account to enable SSH access.

### Notes about adapting the workflow for other DBMSs
1. The `wcss_build.yml` workflow is currently set up to build SQLite by default. You can change the `DBMS` variable to `mysql`, `mariadb`, or `postgresql` to build the corresponding image. However, you will need to modify the apptainer definition files to properly build the image for those DBMSs. These definitions are found in `scripts/apptainers/xxx/` where `xxx` is the database name.
2. This current SQLite image relies on a base image uploaded to Dockerhub, which is built from `scripts/build_docker.sh`. This image contains some dependencies needed for the fuzzing process (this was done due to the lack of root access). If you want to adapt it for other DBMSs, you will probably need to modify this and upload your own base image to Dockerhub.

## Build Instruction (Run on localhost)

### Prerequisite

For ubuntu 22.04:
```
sudo apt install libmysqlclient-dev cmake ninja-build clang pkg-config clang-format libpq-dev libyaml-cpp-dev
```

#### Build Squirrel
1. Clone this repo and run `git submodule update --init`.
2. `cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -Wno-dev`. If you want to compile only the mutator for the specific databases, add `-DXXXXX=ON`, `XXXXX` can be `SQLITE`, `MYSQL` and `POSTGRESQL`. `Mariadb` share the same interface with `MySQL`.
3. `cmake --build build -j`, the binaries are in `build/`.


#### Build AFLplusplus and DBMSs
1. Build aflplusplus: `cd AFLplusplus && make -j && cd ..`.
2. Use `afl-cc` and `afl-c++` to instrument your database.


### Run

#### Configuration

1. Set up a configuration file in `yaml`. Examples can be found in `data/*.yml`.
2. Set the enviroment variable 
```bash
export SQUIRREL_CONFIG=/path/to/config.yml
export AFL_CUSTOM_MUTATOR_ONLY=1
export AFL_CUSTOM_MUTATOR_LIBRARY= REPO_DIR/build/libxxxx_mutator.so
export AFL_DISABLE_TRIM=1
```

#### Normal Mode (SQLite)

Same as AFLplusplus: `afl-fuzz -i input -o output -- sqlite_harness`.

#### Client/Server Mode (MySQL/MariaDB/PostgreSQL)

1. Dry run the database to get the `__afl_map_size` and set it to `AFL_MAP_SIZE`.
2. Run `afl-fuzz -i input -o output -- ./build/db_driver`, it will print the share memory id and wait for 30 seconds.
3. Start the databse server with `export __AFL_SHM_ID=xxxx`.
